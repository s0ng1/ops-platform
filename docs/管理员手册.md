- 版本：v1.0
- 日期：2026-07-29
- 适用对象：负责平台部署、升级、备份与故障处理的系统管理员

## 1. 系统概述与架构

本章帮助管理员建立对平台的整体认识：平台由哪些组件构成、以什么方式采集数据、数据保存多久。

### 1.1 系统简介

内网运维管理平台（ops-platform）是自研的轻量级网络管理系统（NMS），面向内网无外网环境，监控网络设备、安全设备、Windows/Linux 服务器、数据库与应用服务，提供自动发现、网络拓扑、阈值告警、配置备份、Syslog/Trap 接收、IP 地址管理（IPAM）、报表与大屏展示能力。全部采集均为**无 Agent** 方式（ping / SNMP / SSH / 数据库直连 / 应用拨测），被管设备上无需安装任何软件。

技术栈：后端 FastAPI（Python，uvicorn），前端 Vue 3 + Element Plus，时序数据存储 PostgreSQL + TimescaleDB 扩展。

### 1.2 部署架构

生产环境以 docker-compose 一键部署，共三个容器，单台服务器即可承载：

```
浏览器 ──► web（nginx，对外端口，默认 8080）
              │  托管前端静态页 + 反代 /api（含 WebSocket /api/ws）
              ▼
           api（uvicorn，容器内 8100，不对宿主暴露）
              │  业务 API、采集调度、告警引擎、WS 推送、Syslog/Trap 接收
              ▼
           db（TimescaleDB pg15，容器内 5432，不对宿主暴露）
```

| 服务 | 容器名 | 镜像 | 端口 | 数据卷 |
|---|---|---|---|---|
| web | `ops-full-web` | `ops-platform-web:latest` | `${OPS_WEB_PORT:-8080}:80` | 无 |
| api | `ops-full-api` | `ops-platform-api:latest` | 不对外（内部 8100） | 无 |
| db | `ops-full-db` | `timescale/timescaledb:latest-pg15` | 不对外 | `pgdata_full` |

compose 项目名为 `ops-platform-full`，三个容器均在独立内网中通信；只有 web 端口对宿主暴露，数据库端口不暴露到宿主机。

### 1.3 采集方式矩阵

| 采集方式 | 适用对象 | 周期 | 说明 |
|---|---|---|---|
| ping 在线/时延 | 全部设备 | 60s | 产生在线状态与 Ping 时延指标，同时驱动设备上下线告警 |
| SNMP 接口与系统 | 网络/安全设备 | 60s | 接口双向速率/利用率/状态、CPU、内存（按厂商指纹取 OID） |
| Windows SNMP | Windows 主机 | 60s | HOST-RESOURCES-MIB：CPU 多核均值/内存/磁盘分区/进程数 |
| Linux SSH | Linux 主机 | 60s | SSH 读取 /proc 与 df：CPU/内存/磁盘/负载 |
| 数据库探针 | 数据库设备（MySQL/Oracle/SQLServer） | 300s | 只读监控账号直连，采集连接数/QPS/表空间/缓存命中率等 |
| 应用拨测 | 应用设备 | 60s | 五种拨测：HTTP/HTTPS、DNS、TCP 端口、Nginx、Redis |
| IPAM 采集 | 挂 SNMP 凭据的网络设备 | 300s | walk ARP 表/MAC 表，维护 IP 台账与接入位置 |
| 配置备份 | 挂「备份凭据(SSH)」的网络/安全设备 | 6h | SSH 拉取运行配置，按内容 Hash 去重存版本 |
| Syslog / SNMP Trap | 全部可发日志的设备 | 被动接收 | UDP 1514（Syslog）/ UDP 1162（Trap），端口可配 |

### 1.4 数据保留策略

时序指标写入 TimescaleDB hypertable `metrics`，平台在首次启动时自动建表并配置策略：

| 数据 | 保留策略 | 说明 |
|---|---|---|
| `metrics`（原始指标） | 30 天 | 写入 7 天后自动压缩 |
| `metrics_5m`（5 分钟连续聚合） | 180 天 | 供报表与长时间范围曲线使用 |

> 含义：超过 30 天的明细曲线不可查，但 5 分钟粒度的历史趋势与报表可追溯 180 天。磁盘占用随设备数、接口数增长，需定期观察（见 7.5）。

## 2. 环境要求

本章面向准备部署服务器的管理员，列出硬件、软件与网络端口要求。

- Linux 服务器（发行版不限），已安装 **Docker ≥ 20.10** 与 compose v2 插件（`docker compose version` 能输出版本号即可）。
- 建议配置 **4 核 CPU / 8 GB 内存**；规模目标 200~2000 台设备。
- 磁盘 **≥ 20 GB 起步**：三个镜像合计约 1 GB，其余为时序数据与备份空间，占用随设备/接口规模增长，建议定期用 `docker system df -v` 观察。
- 无需外网、无需安装 Python/Node，全部依赖在镜像内。

端口规划：

| 端口 | 协议 | 用途 | 备注 |
|---|---|---|---|
| 8080（默认） | TCP | web 界面与 API | 由 `OPS_WEB_PORT` 配置，冲突时可改 |
| 1514 | UDP | Syslog 接收 | compose 已映射到宿主，防火墙需放行；宿主侧端口由 `OPS_SYSLOG_PORT` 配置 |
| 1162 | UDP | SNMP Trap 接收 | compose 已映射到宿主，防火墙需放行；宿主侧端口由 `OPS_TRAP_PORT` 配置 |
| 8100 | TCP | api 容器内部端口 | 不对外，无需放行 |
| 5432 | TCP | db 容器内部端口 | 不对外，无需放行 |

## 3. 离线部署全流程

本章面向第一次接触本系统的运维人员，按步骤执行即可完成部署。前提：已拿到离线包 `ops-platform-offline-<日期>.tar.gz`（离线包由有外网的打包机运行 `deploy/offline-pack.sh` 生成，内含三个镜像与全部部署文件）。

### 3.1 上传并解压

用 U 盘 / scp 等方式将离线包上传到内网服务器，然后：

```bash
tar xzf ops-platform-offline-*.tar.gz
cd ops-platform-offline-*
```

解压后的目录中包含：`images.tar`（三个镜像）、`docker-compose.yml`、`.env.example`、`nginx.conf`、`Dockerfile.api/.web`、`管理员手册.docx` 与 `用户手册.docx`（另附 .md 源文件）、`wheels/`（备用 wheel 包）。

### 3.2 导入镜像

```bash
docker load -i images.tar
docker images    # 应看到 timescale/timescaledb、ops-platform-api、ops-platform-web 三个镜像
```

导入需几分钟，视磁盘速度而定。

### 3.3 配置环境变量

```bash
cp .env.example .env
vi .env
```

必须填写的项（未设置时 `docker compose up` 会直接报错拒绝启动）：

1. `OPS_DB_PASSWORD`：数据库密码，填一段随机字符串。
2. `OPS_FERNET_KEY`：设备凭据加密密钥，生成命令（服务器没有 Python 时，可在任意一台有 Python 的机器上生成后抄入）：

   ```bash
   python -c "from cryptography.fernet import Fernet;print(Fernet.generate_key().decode())"
   ```

3. `OPS_SECRET_KEY`：JWT 签名密钥（**必须显式设置**，≥32 字节随机串），生成命令：

   ```bash
   python -c "import secrets;print(secrets.token_hex(32))"
   ```

4. `OPS_ADMIN_PASSWORD`：默认管理员初始密码（**必须显式设置**，仅首次启动创建管理员时生效；首登后请立即改密）。

端口冲突时修改 `OPS_WEB_PORT`（默认 8080）。

### 3.4 启动

```bash
docker compose up -d
docker compose ps        # db 应显示 healthy，api/web 为 running
docker compose logs -f api
```

首次启动时后端自动建表（含 TimescaleDB hypertable 与连续聚合），并播种默认管理员与内置告警规则，无需手工初始化。

### 3.5 验证与首次登录

浏览器访问 `http://<服务器IP>:8080`，使用 `.env` 中 `OPS_ADMIN_USERNAME`（默认 `admin`）/ `OPS_ADMIN_PASSWORD` 设定的账号密码登录，**登录后立即在右上角用户菜单「修改密码」中改掉初始密码**（或由 admin 在「用户管理」中重置）。

### 3.6 设备批量入网

平台跑起来后，进入「自动发现」页面，输入要监控的 IP 段（可挂 SNMP 凭据做系统识别）扫描，勾选在线设备批量入库。详细操作见《用户手册》「自动发现」一章；采集所需的各种凭据先在「凭据管理」中录入。

## 4. 配置项说明

本章供管理员查阅全部可配置项。配置载体是离线包根目录的 `.env` 文件（docker compose 启动时读取）；改完任意配置后执行 `docker compose up -d` 生效。

### 4.1 `.env` 配置项

| 变量 | 含义 | 默认值 | 必填 |
|---|---|---|---|
| `OPS_DB_PASSWORD` | 数据库 `ops` 账号密码 | 无 | **是** |
| `OPS_DB_NAME` | 数据库名 | `ops` | 否 |
| `OPS_DB_USER` | 数据库账号 | `ops` | 否 |
| `OPS_DB_IMAGE` | 数据库镜像 | `timescale/timescaledb:latest-pg15` | 否；拉不到 timescale 镜像时可用 `postgres:16-alpine` 兜底（时序压缩/连续聚合不可用，且需 `down -v` 重建卷） |
| `OPS_DB_POOL_SIZE` | 后端数据库连接池大小 | `20` | 否 |
| `OPS_DB_MAX_OVERFLOW` | 连接池溢出上限 | `40` | 否 |
| `OPS_FERNET_KEY` | 设备凭据 Fernet 加密密钥 | 无 | **是**（更换=已存凭据全部失效，见 6.2） |
| `OPS_SECRET_KEY` | JWT 签名密钥（≥32 字节随机串） | 无 | **是**（compose 强制必填） |
| `OPS_WEB_PORT` | web 服务对外端口 | `8080` | 否 |
| `OPS_ADMIN_USERNAME` | 首次启动创建的默认管理员账号 | `admin` | 否（仅首启生效） |
| `OPS_ADMIN_PASSWORD` | 默认管理员初始密码 | 无 | **是**（仅首启生效，首登后立即改密） |

Syslog/Trap 接收（设备主动发日志到平台）默认启用，离线包的 compose 已将 api 容器的 UDP 1514/1162 映射到宿主，只需在服务器防火墙放行这两个 UDP 端口，并把设备的 syslog/trap 目的地址指向平台服务器即可。宿主侧端口冲突时，在 `.env` 中改 `OPS_SYSLOG_PORT` / `OPS_TRAP_PORT`（只改宿主侧，容器内固定 1514/1162），设备侧目的端口相应调整。

> **建议配置来源白名单**：内网任意主机可向 1514/1162 发送 UDP 报文伪造日志与告警。在 `.env` 中设置 `OPS_SYSLOG_ALLOW` / `OPS_TRAP_ALLOW`（逗号分隔 IP/CIDR，如 `192.168.8.0/24,10.0.0.1`）后，只有命中白名单的来源报文才会被接收；留空表示全部接收。

### 4.2 后端其余 `OPS_*` 环境变量

以下变量定义在后端配置中，一般无需修改；如有需要可按同名环境变量注入（开发/裸机部署场景使用，docker 全栈部署通常用不到）。

| 变量 | 含义 | 默认值 |
|---|---|---|
| `OPS_APP_NAME` | 应用名称 | `内网运维管理平台` |
| `OPS_DATABASE_URL` | 数据库连接串 | 开发默认 SQLite；docker 全栈由 compose 自动注入指向 db 容器 |
| `OPS_TOKEN_EXPIRE_HOURS` | 登录态（JWT）有效期，小时 | `12` |
| `OPS_MONITOR_INTERVAL` | ping 监控轮询周期，秒 | `60` |
| `OPS_LOG_RECEIVER_ENABLED` | Syslog/Trap 接收器开关 | `true` |
| `OPS_SYSLOG_PORT` | Syslog 监听 UDP 端口 | `1514` |
| `OPS_TRAP_PORT` | SNMP Trap 监听 UDP 端口 | `1162` |
| `OPS_SYSLOG_ALLOW` | Syslog 来源 IP 白名单（逗号分隔 IP/CIDR，空=全部） | 空 |
| `OPS_TRAP_ALLOW` | Trap 来源 IP 白名单（同上） | 空 |
| `OPS_SSRF_BLOCK_LOOPBACK` | 应用拨测 SSRF 防护是否封回环地址 | `true` |

## 5. 日常运维

本章覆盖备份恢复、日志查看、升级与启停四类例行操作。以下命令默认在离线包解压目录（含 `docker-compose.yml`）下执行。

### 5.1 数据备份与恢复

平台全部业务数据都在数据库命名卷 `pgdata_full` 中，推荐定时做逻辑备份：

```bash
# 备份（输出文件建议放到独立磁盘目录，如 /backup/）
docker exec ops-full-db pg_dump -U ops -d ops | gzip > /backup/ops-backup-$(date +%F).sql.gz

# 恢复
zcat /backup/ops-backup-2026-07-29.sql.gz | docker exec -i ops-full-db psql -U ops -d ops
```

cron 每日备份示例（`crontab -e`，每天 02:30 执行，保留最近 30 份；注意 cron 中 `%` 必须转义为 `\%`）：

```cron
30 2 * * * docker exec ops-full-db pg_dump -U ops -d ops | gzip > /backup/ops-backup-$(date +\%F).sql.gz && find /backup -name 'ops-backup-*.sql.gz' -mtime +30 -delete
```

**同时必须备份 `.env` 文件**（尤其 `OPS_FERNET_KEY` 与 `OPS_DB_PASSWORD`）：丢失 `OPS_FERNET_KEY` 后，数据库中所有已加密的设备凭据将无法解密，只能全部重录。

### 5.2 查看日志

```bash
docker compose ps                 # 容器状态总览
docker compose logs -f api        # 后端日志（采集、告警、API 报错都在这里）
docker compose logs -f db         # 数据库日志
docker compose logs -f web        # nginx 访问/错误日志
docker logs --tail 200 ops-full-api   # 等价查看方式
```

### 5.3 升级流程

1. 在打包机上重新运行 `deploy/offline-pack.sh` 得到新版 tar.gz，上传到现场服务器。
2. 解压到**新目录**，执行 `docker load -i images.tar` 导入新镜像。
3. 把旧目录的 `.env` 复制到新目录（**`OPS_FERNET_KEY`、`OPS_DB_PASSWORD` 必须保持不变**）。
4. 在新目录执行 `docker compose up -d`：compose 会用新镜像重建 api/web 容器，db 数据卷不动。
5. 表结构变更由后端启动时自动补齐（新增表/列自动处理）。

### 5.4 服务启停

```bash
docker compose stop           # 停止全部服务（保留容器与数据）
docker compose start          # 启动
docker compose restart api    # 只重启后端
docker compose down           # 停止并删除容器（数据卷保留）
```

> **警告：`docker compose down` 任何时候都不要加 `-v`**——`-v` 会连同 `pgdata_full` 数据卷一起删除，全部监控数据即刻丢失且不可恢复。

## 6. 安全基线

本章给出上线前后必须完成的安全动作清单。

1. **首登立即改初始密码**：默认管理员账号与初始密码由 `.env` 的 `OPS_ADMIN_USERNAME` / `OPS_ADMIN_PASSWORD` 设定（仅首次启动播种时生效），登录后第一时间修改；此后改 `.env` 里的 `OPS_ADMIN_PASSWORD` 不再影响已创建的管理员。
2. **四个密钥/口令显式配置并妥善备份**：`OPS_DB_PASSWORD`、`OPS_FERNET_KEY`、`OPS_SECRET_KEY`、`OPS_ADMIN_PASSWORD` 均应在 `.env` 中显式设置（compose 已强制必填），`.env` 文件本身纳入备份（建议与数据库备份分开存放）。
3. **`OPS_FERNET_KEY` 一经设定不可更换**：平台中所有设备凭据（SNMP 团体名/v3 密钥、SSH 密码、数据库密码）均用该密钥以 Fernet 对称加密后落库。**更换密钥 = 数据库里全部已加密凭据无法解密，所有设备采集失效，只能逐台重新录入凭据。** 升级、迁移、换机都必须沿用原密钥。
4. **按角色建账号，不用 admin 当日常账号**：三种角色的能力边界见《用户手册》1.2 节。建议：admin 账号仅用于用户管理与审计查看；日常运维建 operator（操作员）账号；仅查看人员建 viewer（只读用户）账号。
5. **密码与登录态**：用户密码以 PBKDF2-HMAC-SHA256 哈希存储（创建/改密要求至少 8 位且同时含字母与数字）；登录态为 JWT，默认 12 小时过期；登录接口带防爆破限流（同用户名连续失败锁定、同 IP 超阈值锁定）；通知渠道密钥（SMTP 密码、Webhook 地址）同样 Fernet 加密落库，且编辑时不回显。
6. **网络面收敛**：数据库端口不暴露宿主机；对外仅开放 web 端口与（如启用）Syslog/Trap 两个 UDP 端口。
7. **敏感数据访问控制**：设备配置备份全文与差异比对仅 admin/operator 可读（viewer 只能看版本列表）；Redis 拨测口令在接口回显时脱敏为 `******`；应用拨测目标做了 SSRF 防护（封禁回环/链路本地/云元数据/组播等保留段）。
8. **SSH 主机指纹 TOFU**：平台对 SSH 采集与配置备份做「首次信任、后续校验」的主机指纹校验（存 `backend/data/ssh_known_hosts.json`），指纹不匹配会拒绝连接并记日志，防中间人。首次连接即记录指纹，设备重装/更换主机密钥后需删除该文件中的对应记录重新学习。
9. **HTTPS（可选）**：默认走 HTTP 明文，内网建议在 nginx 层启用 HTTPS（见 `deploy/nginx.conf` 注释的 443 配置块与 7.11），或至少明确部署边界与网络隔离；nginx 已默认返回 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy` 安全响应头。

## 7. 故障排查 FAQ

本章按「现象 → 排查 → 处置」组织常见问题，供值班管理员快速定位。

### 7.1 容器反复重启 / db 健康检查失败

- 排查：`docker compose ps` 看哪个容器异常；`docker compose logs db`、`docker compose logs api` 看具体报错。
- 常见原因与处置：
  - db 起不来多为数据卷损坏或磁盘满：`df -h` 确认磁盘空间。
  - api 反复重启且日志报数据库连接失败：等 db 变为 `healthy` 后 api 会自动拉起；若 db 一直 unhealthy，按 7.7 处理。
  - `docker compose up -d` 直接报错退出：检查 `.env` 是否缺少 `OPS_DB_PASSWORD` / `OPS_FERNET_KEY`（这两项未设置时 compose 会直接拒绝启动并提示）。

### 7.2 登录接口报 500 / compose 拒绝启动

- 现象一：`docker compose up` 直接报错退出，提示需要设置 `OPS_SECRET_KEY` / `OPS_ADMIN_PASSWORD`。
- 原因：`.env` 缺少 `OPS_SECRET_KEY`、`OPS_ADMIN_PASSWORD` 或为空（compose 已对这两项强制必填）。
- 处置：按 3.3 生成合法随机值填入 `.env`，重新 `docker compose up -d`。
- 现象二：页面能打开但登录报服务器错误，api 日志出现 `HMAC key must not be empty`。
- 原因：`.env` 里 `OPS_SECRET_KEY` 是空串（如 `OPS_SECRET_KEY=`）。
- 处置：把该行改成合法随机串（`python -c "import secrets;print(secrets.token_hex(32))"`）后 `docker compose up -d` 重启 api。

### 7.3 页面能打开，但实时推送不工作（顶栏圆点灰色）

- 现象：页面正常，但新告警不弹通知、设备状态不自动刷新，顶栏左侧圆点为灰色（正常为绿色呼吸点）。
- 排查：平台实时推送走 WebSocket（`/api/ws`）。随平台交付的 nginx 已配置 Upgrade 头，直接访问 `http://服务器:8080` 时 WS 可用；若在平台前面又套了一层上层反向代理（如统一门户、硬件 LB），需要在该层同样放行 WebSocket（Upgrade/Connection 头，并放宽读超时）。
- 处置：在上层代理补 WebSocket 配置，或绕过代理直连平台端口验证。

### 7.4 设备在线但 SNMP 采集不出数

- 排查顺序：
  1. 设备列表点「立即探测」：在线/时延正常说明 ping 通，问题在 SNMP 层。
  2. 核对设备绑定的凭据：团体名（v2c）或 v3 用户名/认证加密参数是否与设备配置一致，端口是否非默认 161。
  3. 设备侧：SNMP 服务是否启用、是否有 ACL 限制源地址（需放行平台服务器 IP）、中间防火墙是否放行 UDP 161。
  4. `docker compose logs -f api` 看对应采集任务的报错。
- 同类问题对照：Linux 主机不出数查 SSH 凭据与 22 端口连通性；数据库不出数查监控账号权限与端口；Windows 主机确认 SNMP 服务已安装并配好团体名。

### 7.5 磁盘增长过快

- 排查：`docker system df -v` 看 `pgdata_full` 卷、容器日志、镜像各占多少。
- 处置：
  - 时序数据本身是主要增长点：原始指标保留 30 天、5 分钟聚合 180 天，属设计行为；设备/接口规模越大增长越快，按 2 章建议预留并持续观察。
  - 检查备份目录（如 `/backup`）是否只增不减，按 5.1 的 `find -mtime` 方式加保留期清理。
  - 容器日志：`docker logs` 输出长期累积也会占盘，可在 daemon 层配置 json-file 轮转（`log-opts max-size/max-file`），改完需重启 Docker。

### 7.6 忘记 admin 密码

平台没有自助找回通道，按以下步骤在服务器上重置（以重置为 `NewPassw0rd` 为例）：

```bash
# 1) 在 api 容器内用平台同款算法生成密码哈希
HASH=$(docker exec ops-full-api python -c "from app.core.security import hash_password; print(hash_password('NewPassw0rd'))")

# 2) 直接更新 users 表
docker exec -i ops-full-db psql -U ops -d ops -c "UPDATE users SET password_hash='$HASH' WHERE username='admin';"
```

重置后用新密码登录，并立即再改一次。若库中还有其它启用状态的 admin 账号，更简单的方式是用它登录后在「用户管理」中处理。

### 7.7 数据库连不上 / api 日志报认证失败

- 排查：`docker compose ps` 确认 db 是否 healthy；api 日志报 `password authentication failed` 则说明密码不匹配。
- 关键认知：**数据库密码以卷首次初始化时的 `OPS_DB_PASSWORD` 为准**——初始化完成后再改 `.env` 里的 `OPS_DB_PASSWORD`，不会修改数据库里已有的密码，反而导致 api 连不上。
- 处置（二选一）：
  - 把 `.env` 的 `OPS_DB_PASSWORD` 改回初始化时的值；
  - 或进入数据库手工改密：`docker exec -it ops-full-db psql -U ops -d ops -c "ALTER USER ops PASSWORD '新密码';"`，再把 `.env` 改成同样的新密码并 `docker compose up -d`。

### 7.8 端口被占用

- 现象：`docker compose up -d` 报 `address already in use`。
- 处置：改 `.env` 的 `OPS_WEB_PORT` 为空闲端口（如 18080）后重新 `up -d`。
- 特殊情况：在 WSL2（mirrored 网络）上，Windows 宿主侧程序占用端口时，WSL 内 `ss` 可能看不到监听但绑定仍冲突，同样改 `OPS_WEB_PORT` 规避。

### 7.9 Syslog / Trap 收不到日志

- 排查：
  1. compose 已内置 UDP 端口映射——确认 api 容器运行正常，且服务器防火墙放行了 1514/1162 两个 UDP 端口（如改过 `OPS_SYSLOG_PORT`/`OPS_TRAP_PORT`，以改后端口为准）。
  2. 在服务器上确认监听：`docker exec ops-full-api ss -lun | grep -E '1514|1162'`。
  3. 设备侧配置：网络设备的 syslog 主机 / trap 目的地址是否指向平台服务器 IP 与正确端口。
- 现象对照：能收到日志但不产生告警，属于「日志规则」未命中或来源 IP 未入库为设备，见《用户手册》告警中心「日志规则」一节。

### 7.10 `OPS_FERNET_KEY` 丢失或更换后，设备全部采集失败

- 现象：api 日志出现凭据解密失败（`InvalidToken`），所有挂凭据的设备采集报错。
- 预防：`.env` 纳入备份（5.1）；升级迁移严格沿用原密钥（5.3）。
- 处置：找回原密钥填回 `.env` 是唯一无损恢复方式；确实找不回时，只能在「凭据管理」中逐条重新录入所有凭据。

### 7.11 启用 HTTPS

- 平台默认走 HTTP 明文（内网常见）；如需 HTTPS：准备 `server.crt` / `server.key`，在 `deploy/docker-compose.full.yml` 的 web 服务取消注释 443 端口映射与 `./certs:/etc/nginx/certs:ro` 卷挂载，把证书放入 `deploy/certs/`，并在 `deploy/nginx.conf` 取消注释末尾的 443 server 块后 `docker compose up -d`。
- 说明：nginx 已默认返回 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy` 三个安全响应头（HTTP/HTTPS 均生效）；`Content-Security-Policy` 因可能影响图表库渲染，以注释形式预留，启用前请用构建产物验证。
