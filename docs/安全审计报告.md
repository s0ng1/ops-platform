## 严重（可直接导致认证失效 / 越权）

### 1. 生产部署使用弱默认密钥与默认管理员口令
- `backend/app/core/config.py`：`secret_key = "dev-only-secret-change-me-0123456789abcdef"`、`admin_username="admin"`、`admin_password="admin123"`。
- `deploy/docker-compose.full.yml`：`OPS_SECRET_KEY` 回退到 `dev-only-secret-change-me-0123456789abcdef`，`OPS_ADMIN_PASSWORD` 回退到 `admin123`；`deploy/.env.example` 中 `OPS_SECRET_KEY` 仍是注释状态。
- 后果：按默认方式部署时，攻击者知道 `sub=1`（admin 通常为 1）即可用公开的 JWT 密钥伪造管理员 token（`get_current_user` 用 `int(payload["sub"])` 回查用户，`require_roles` 用库里的 `role`，伪造 `sub=1` 即得 admin）；或直接用 `admin/admin123` 登录。
- 建议：`OPS_SECRET_KEY` 与 `OPS_ADMIN_PASSWORD` 改为 `:?` 强制必填（同 `OPS_FERNET_KEY`），首启后强制改密，并在文档中去除明文默认口令。

### 2. 登录接口无速率限制、无账户锁定
- `backend/app/api/auth.py` 的 `POST /api/auth/login` 只写审计、无节流或失败锁定，配合第 1 点可被在线爆破。
- 建议：按 IP + 用户名做登录限流，连续失败锁定/退避。

## 高（敏感信息泄露 / SSRF）

### 3. Redis 拨测口令明文存储并随设备接口回显
- `backend/app/api/schemas.py`：`DeviceOut.probe_config: dict = {}`；`backend/app/api/devices.py` 的 `_to_out` 直接 `model_validate` 原样返回 `device.probe_config`。
- `backend/app/collectors/middleware_probe.py`：Redis 的 `password` 存在 `probe_config`，未走加密的 `credentials` 表。
- 后果：`GET /api/devices`、`GET /api/devices/{id}` 对任意已登录用户（含 viewer）返回 Redis 口令明文，且与 SNMP/SSH/DB 凭据「Fernet 加密落库」的设计不一致。
- 建议：Redis 口令归入 `credentials` 表加密存储，或至少在 `DeviceOut` 中脱敏 `probe_config` 的 password 字段。

### 4. 应用拨测可被 operator 用作 SSRF / 内网探测
- `backend/app/api/devices.py` 允许 `application` 类型 `ip` 为任意域名/主机，`probe_config` 可自由配置。
- `backend/app/collectors/app_probe.py` / `middleware_probe.py` 由服务端发起 http/https、dns、tcp（`device.ip:port`）、redis 连接，目标完全由 operator 控制，无协议/目标段限制、无内网地址黑名单。
- 后果：operator（较低的写权限角色）可让后端访问 `169.254.169.254` 云元数据、内网管理口、任意端口，形成内网 SSRF/端口扫描。
- 建议：限制拨测目标（禁止 loopback/link-local/元数据地址，或引入目标白名单/审批），并限制重定向与响应体大小。

### 5. 设备配置备份明文入库且低权限可读
- `backend/app/collectors/config_backup.py` 将 `display current-configuration` 等完整配置写入 `ConfigBackup.content`（未加密）。
- `backend/app/api/config_backup.py`：`GET /api/devices/{id}/config-backups/{backup_id}` 返回 `content` 全文，`/diff` 返回差异，均只要求 `get_current_user`（viewer 亦可）。
- 后果：设备配置常含 SNMP community、本地用户口令等，被低权限用户读取。
- 建议：配置备份按角色授权（至少 operator/admin），或对 content 做加密存储。

## 中（网络 / 凭据 / 审计）

### 6. Syslog / SNMP Trap 接收器无认证，可伪造日志与告警
- `deploy/docker-compose.full.yml` 把 UDP 1514/1162 映射到宿主 `0.0.0.0`；`backend/app/core/logreceiver.py` 的 syslog 不校验来源；`backend/app/collectors/snmp.py` 的 `start_trap_receiver` 明确「任意 community 都接收」。
- 后果：内网任意主机可灌假日志、触发假告警（虽有 5 分钟去重，仍可造成告警风暴/欺骗）。
- 建议：来源 IP 白名单、去重/限速、trap community 校验。

### 7. SSH 采集与配置备份关闭主机指纹校验
- `backend/app/collectors/linux_ssh.py` 与 `config_backup.py` 均使用 `asyncssh.connect(..., known_hosts=None, ...)`。
- 后果：存在 MITM 风险，设备 SSH 口令可被窃取。
- 建议：首次记录并校验 host key（known_hosts / TOFU）。

### 8. WebSocket 把 JWT 放在 URL 查询串
- `backend/app/api/ws.py`、`frontend/src/stores/ws.js`：`/api/ws?token=<jwt>`。
- 后果：token 会进入 nginx access log、浏览器历史、Referer。
- 建议：改用带 `Authorization` 头鉴权或短期一次性 ticket。

### 9. 审计日志记录的客户端 IP 在反代下失效
- `backend/app/core/audit.py` 的 `client_ip` 取 `request.client.host`（直连对端），但 `deploy/nginx.conf` 已设置 `X-Forwarded-For`，后端未解析。
- 后果：审计日志里的 IP 实际是 nginx 容器 IP，失去来源追踪价值。
- 建议：读取并信任 `X-Forwarded-For`（配合受信代理配置）。

### 10. 全程明文 HTTP
- `deploy/nginx.conf` 仅 `listen 80`，无 TLS；登录口令、JWT、配置备份均在网络明文传输。
- 建议：内网也建议上 HTTPS，或至少明确部署边界与网络隔离。

## 低 / 建议

- 密码策略弱：`backend/app/api/schemas.py` 中用户创建/改密密码仅 `min_length=6`、无复杂度；改密后旧 token 不失效。
- 用户名枚举：`backend/app/api/auth.py` 登录时 `user is None` 会短路跳过 `verify_password`，存在轻微时序差。
- `import_devices` 不校验 IP 且无数量上限：`backend/app/api/discovery.py` 的 `ImportIn.ips` 直接入库，可灌入脏数据/造成库膨胀（`scan` 路径有 `ipaddress` 校验，`import` 路径没有）。
- 报表导出潜在 Excel 公式注入：`backend/app/api/reports.py` 用 openpyxl 直接写入设备名/IP 等字符串，operator 可控设备名，若以 `=` 开头可能被当作公式（低危）。
- 无安全响应头：nginx 未设置 CSP、`X-Content-Type-Options` 等。

## 已做对的（无需整改）

- SNMP v2c/v3、SSH、数据库凭据整体 Fernet 加密落库，凭据接口不回显明文。
- 通知渠道（SMTP 口令、webhook）也加密存储（`backend/app/models/alert.py` 的 `NotifyConfig`）。
- RBAC 在后端强制（写操作 operator、用户管理 admin），不是只靠前端路由守卫。
- 密码哈希使用 PBKDF2-HMAC-SHA256（120k 迭代）+ `hmac.compare_digest`。
- SQL 基本走 ORM；`backend/app/api/reports.py` 的原生 SQL 使用 `bindparam` 参数绑定，未发现 SQL 注入。
- `backend/app/collectors/scanner.py` 的 ping 使用 `create_subprocess_exec` 列表参数（非 shell），IP 经 `ipaddress` 校验。
- `.gitignore` / `.dockerignore` / `deploy/offline-pack.sh` 正确排除 `backend/data/`、`deploy/.env`、`deploy/offline/`，未把 `fernet.key` 或真实 `.env` 打入镜像/离线包。
- `deploy/Dockerfile.api` 以非 root 用户运行；CORS 限制到 localhost 而非 `*`；拓扑画布 `innerHTML` 有 `escapeHtml` 转义。

## 整改优先级建议

1. 先处理认证高危：默认密钥/默认管理员口令、登录防爆破。
2. 再处理敏感信息与越权：Redis 口令回显、SSRF、配置备份越权读取。
3. 最后做网络与审计加固：Syslog/Trap 认证、SSH host key、WS token、审计 IP、HTTPS。
