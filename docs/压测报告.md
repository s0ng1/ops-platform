# M4 压测报告：模拟 2000 台设备 + Redis 引入评估

日期：2026-07-22 · 脚本：`scripts/bench.py` · 原始数据：`logs/bench-{500,1000,2000}.json`

> 第 5 期优化后的复测验收（2026-07-23）见文末「8. M5 复测（第 5 期优化验收）」：2000 台周期 17.6s，**已达标**；本文 1~7 节保留第 4 期原始结论作历史对照。

## 结论先行

1. **现状（代码不改）扛不住 2000 台**：完整采集周期墙钟 106s > 60s 采集间隔，且随规模近 O(N²) 恶化（500→1000→2000 台为 15s→38s→106s）。500 台轻松、1000 台勉强（余量仅 1.6 倍）。
2. **瓶颈不在「单机单进程 asyncio」架构本身**，而是两个可定位、可修复的实现问题：
   - 告警引擎在 ping 监控循环里**逐台设备调用** `evaluate_points`，每次调用都全量加载 devices 表 → O(N²)，2000 台时独占 ~79s/周期；
   - 同步 SQLAlchemy 会话直接跑在协程里，全部 DB 操作串行化在事件循环单线程上；且 `check_device` 在 ping/SNMP 的 await 期间持有连接与事务，**生产默认连接池（5+10）下 50 台规模就会周期性冻结事件循环**（每次 30s 池超时）。
3. **Redis 结论：不引入**。瓶颈与「采集队列/状态缓存/WS 推送」无关，引 Redis 解决不了上述两点，反而增加部署与运维复杂度。按第 5 节建议修复后，2000 台估算周期时间可落回 60s 以内，单进程 asyncio 足够覆盖 200~2000 台设计目标。

## 1. 压测方法

不真实采集，把网络层 stub 掉，压的是**调度器 + ping 监控循环 + 告警引擎 + DB 写入**这条真实代码链路：

- 各采集器在既有注入点替换网络层（`fetch_walk`/`run_commands`/`query`，ping 与 SNMP 系统信息同样 stub），返回合成数据（接口计数器递增、CPU/内存随机、device_online=1），单点耗时 5~20ms 模拟 LAN 延迟；
- 调度器任务（snmp_metrics / windows_snmp / linux_ssh / db_probe）、`monitor_loop.run_check_once`、告警引擎（含 2 条内置规则）、metrics hypertable 批量入库全部走生产代码与生产默认并发（COLLECT_CONCURRENCY=CHECK_CONCURRENCY=50）；
- 设备配比按采集矩阵：network 40% / security 10% / server_windows 25% / server_linux 20% / database 5%，网络/安全设备各 8 个接口；
- 每周期点数（稳态）：500 台 11,825 / 1000 台 23,650 / 2000 台 47,300，折合 2000 台时 ~788 点/s（≈24 指标/台/min，略高于设计口径的 20 指标/台/min、666 点/s，偏保守）；
- 数据隔离：独立 `ops_bench` 库（自动建库、跑完 DROP），不碰 dev 的 `ops` 库；hypertable 结构与生产一致（为消除计时干扰摘掉了 retention/compression/cagg 策略后台作业，见 4.3）。

用法：

```bash
# 密码从 OPS_DB_PASSWORD 环境变量或 deploy/.env 读取，不落盘
backend/.venv/bin/python scripts/bench.py --devices 2000 --cycles 3 \
    --pool-size 30 --json logs/bench-2000.json
# 常用参数：--ifaces 接口数 --latency-min/max 单点延迟 --concurrency 覆盖协程池上限
# --pool-size 0=保持生产默认池(5+10)  --keep 保留 bench 库  --dbname 换库名
```

## 4. 瓶颈分析

### 4.1 第一瓶颈：告警引擎 O(N²) 评估（~79s/周期 @2000 台）

`monitor_loop.check_device` 每探一台设备就调一次 `evaluate_points`（2 个点）；而 `evaluate_points` 每次调用都 `db.query(Device).all()` 全量加载设备表 + 全量加载规则。2000 台 → 每周期 2000 次调用 × 加载 2000 行设备 ≈ 400 万行 ORM 物化，加每点每条匹配规则的 `_resolve` SELECT。评估总耗时 78.8s，占周期墙钟 75%，且同步执行在事件循环线程上，连带拖慢所有并发任务（snmp_metrics 任务 103s 里大部分是等评估/等插入的连锁阻塞）。

调度器侧 4 个任务的评估（每任务一次、批量传入）本身只需秒级——同样的引擎，调用方式决定了 O(N) 还是 O(N²)。

### 4.2 第二瓶颈：同步 DB 会话 + 默认连接池耗尽冻结（生产默认配置下 50 台即现）

- `check_device` 先 `db.get(Device)`（检出连接、事务开启），再 `await ping` / `await get_system_info`——**await 期间一直持有连接与事务**。50 并发探测就需要 ~50 个连接，而 `database.py` 用 SQLAlchemy 默认池（pool_size=5 + overflow=10 = 15）。
- 池耗尽时检出操作**同步阻塞事件循环线程**，30s 池超时内整个进程停摆（协程全部饿死），超时抛错后被静默吞掉、再来一轮。实测：50 台 × 2 周期用生产默认池跑 10 分钟未完成，`pg_stat_activity` 显示 15 个 `idle in transaction` 连接、进程 0% CPU。
- 本报告三档数据均用 `--pool-size 30`（60 连接）重配后测得，否则 500/1000/2000 全部无法完成。**即生产当前默认配置的实际可用规模上限远低于 500 台。**
- 同步会话的另一面：所有 DB 读写（含 4.7 万行批量 insert、每条 `_resolve` SELECT）都串行占事件循环，asyncio 的并发红利在 DB 段完全失效。

### 4.3 次要风险：Timescale 策略作业与长事务的锁排队

压测中发现：retention 策略后台作业（建策略后首跑）对 metrics chunk 请求 AccessExclusiveLock，排在 4.2 所述「idle in transaction」长事务之后；后续普通 SELECT 又排在排他锁请求之后，其中一个 SELECT 恰好由事件循环同步发出 → 循环冻结、持事务的协程无法恢复，形成跨进程循环等待，首周期卡死 ~300s。bench 侧已规避（bench 库摘掉策略作业）。生产上策略早已存在、作业在闲时调度，触发概率低，但建议给 Timescale 策略作业配置 `lock_timeout`，并随 4.2 的修复消除长事务。

### 4.4 不是瓶颈的部分

- **采集并发/协程池**：采集段（stub 网络）很轻——linux_ssh 全任务 13.5s、db_probe 3.9s；即使真实单点耗时放大 10 倍（SSH 建连 ~1s/台），50 并发 × 60s 仍可覆盖 ~3000 台。COLLECT_CONCURRENCY=50 足够。
- **DB 批量写入**：单任务 4.2 万行单事务 insert 约秒级~十秒级，hypertable 写入不是瓶颈。
- **内存/CPU**：RSS 峰值 157MB，单核占用为主，余量充足。
- **WS 推送**：进程内广播器在无告警风暴时开销可忽略（本次评估点数 5.1 万/周期未触发 fire 风暴）。

## 5. 优化建议（按优先级，均不需引新组件）

1. **告警评估批量化**（收益最大，O(N²)→O(N)）：`monitor_loop` 一轮只调一次 `evaluate_points`（汇总全部设备的 device_online/ping_latency 点批量传入）；引擎内 devices/rules 每次调用只加载一次。预计 2000 台周期 −70s 以上。
2. **check_device 不持连接过 await**：先 ping/SNMP 再开会话回写。消除连接占用与长事务，默认池也不再被探测循环耗尽。
3. **DB 操作移出事件循环**：同步会话调用包 `asyncio.to_thread`（或中期评估 asyncpg 异步驱动），让 DB 段真正并发；连接池按 `CHECK_CONCURRENCY + 任务余量` 显式配置（如 pool_size=30、max_overflow=30）。
4. **引擎内 `_resolve` 批量化**：按 (rule_id, device_id, labels_key) 一次 IN 查询取代逐点 SELECT。
5. 给 Timescale 策略作业设 `lock_timeout`（次要，见 4.3）。

做完 1+2 的保守估算：2000 台周期 ≈ 采集段 ~15s + 评估 ~5s + 入库 ~10s + 监控循环 ~10s（并发交叠后）≈ **20~35s < 60s**，2000 台可扛；再做 3 余量更大。

## 6. Redis 评估结论：**不引入**

| Redis 候选用途 | 评估 |
|---|---|
| 采集队列 | 瓶颈不在采集分发，协程池远未饱和（4.4）；队列解决不了 O(N²) 评估与同步会话问题 |
| 状态缓存 | 设备状态读写在批量评估修复后每周期仅数次批量 SQL，无需缓存层 |
| WS 推送/pub-sub | 广播器为单进程内存实现，当前无多实例需求；告警风暴未构成开销（4.4）。未来多实例部署时按 AGENTS.md 既定方案只换 `core/broadcast.py` 一个文件 |

维持 AGENTS.md 既有决策（「Redis 非必须，推迟」）。触发重新评估的条件：多实例/水平扩展部署、单进程修复后仍无法压进 60s、或设备规模超 ~3000 台。

## 7. 已知局限

- 网络层为 stub：不含真实 SNMP 协议栈（pysnmp to_thread）、SSH 建连（~0.1~1s/台，远重于 stub 的 5~20ms）与超时长尾。采集段结论（4.4）按 10 倍耗时余量估算仍成立，但真机联调时应复核采集段耗时。
- 未压 FastAPI 请求面（API/WS 并发），仅压采集-评估-入库链路。
- 评估用规则为 2 条内置规则；规则数大幅增加会线性放大评估耗时（批量修复后仍建议关注）。

### 8.2 结论

1. **2000 台验收线通过**：周期墙钟 17.6s < 60s，落在第 4 期估算区间（20~35s）下沿；增长曲线由近 O(N²)（15→38→106，≈N^1.9）回到**线性**（4.3→8.7→17.6，≈N^1.0）。
2. 告警引擎开销 78.8s→0.58s（−99%），O(N²) 彻底消除；默认池（20+40）下 50 台冻结问题不复现（冒烟 50 台 1 周期 0.5s 通过）。
3. 剩余瓶颈（不阻塞验收）：墙钟现由 **ping 监控循环**（18.4s）决定，其内部每台设备 2 次 to_thread 短会话（读快照 + 写回）共 ~4000 次 DB 往返是主要开销；snmp_metrics 任务 9.5s 次之。如需进一步压缩，可将监控循环的读/写各合并为每轮一次批量 SQL，预计 2000 台可到 ~10s——属于可选优化，本期不做。
4. RSS 峰值 157→232MB（+48%）：评估批量化后单批点数更大（单任务 4.2 万点一次性物化 + firing 事件预加载字典），绝对值仍充裕，可接受。
5. Redis 结论维持「不引入」：线性增长 + 3.4 倍余量下，2000 台设计目标单进程 asyncio 已覆盖。
